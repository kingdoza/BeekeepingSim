### [질문 1]

1. 아이템 행동의 실제 실행 주체
- 질문 내용: `UItemAction` 계층이 아이템의 사용/소모/배치 행동을 어디까지 직접 수행할지 확정이 필요하다.
- 필요한 이유: 이 선택에 따라 아이템 액션이 월드, 캐릭터, 인벤토리와 직접 결합될지, 아니면 실행 요청만 만들고 별도 시스템이 실제 적용을 담당할지가 달라진다. 특히 `PlaceAction`처럼 월드 변경이 큰 행동의 구조가 크게 달라진다.
- 선택지
  - 옵션 A: `UItemAction` 이 직접 실행까지 담당한다. 소비, 배치, 사용 모두 action 객체가 수행한다.
  - 옵션 B: `UItemAction` 은 실행 가능 여부와 요청 데이터만 만들고, 실제 실행은 캐릭터/인벤토리/월드 시스템이 담당한다.
  - 옵션 C: 단순 행동은 `UItemAction` 이 직접 실행하고, 월드 영향이 큰 행동은 별도 시스템에 위임한다.

### [질문 9]

1. 핫바 만석 시 획득 처리
- 질문 내용: 핫바에 빈 슬롯이 없고, 기존 스택도 모두 가득 찬 상태에서 아이템을 획득 시도하면 어떻게 처리할지 확정이 필요하다.
- 필요한 이유: 별도 인벤토리를 두지 않기로 했기 때문에, 이 경우가 곧 최종 획득 성공/실패 조건이 된다.
- 선택지
  - 옵션 A: 획득 실패 처리하고 월드 아이템은 그대로 둔다.
  - 옵션 B: 획득 실패 처리하되 일부만 들어갈 수 있으면 일부만 획득한다.
  - 옵션 C: 핫바의 특정 슬롯 교체 규칙을 적용해 강제로 획득한다.

### [질문 2]

1. 선택 아이템 메시 표시 책임 위치
- 질문 내용: 현재 선택된 hotbar 아이템의 메시를 일반 상태에서는 화면 오른쪽 구석에 들고 있는 형태로 표시하고, `EngagedFocus` 에서는 같은 메시를 커서를 따라 움직이게 만들 때, 이 표시 책임을 어느 구조가 가져야 할지 확정이 필요하다.
- 필요한 이유: `UBeekeeperHotbarComponent` 는 현재 상태 오너 역할에 가깝고, 메시 표시까지 직접 담당할지, 캐릭터의 별도 시각화 컴포넌트로 분리할지에 따라 책임 분리와 향후 확장성이 달라진다.
- 선택지

  - 옵션 C: 선택 아이템 시각화 전용 별도 컴포넌트(예: `UBeekeeperHeldItemVisualizerComponent`)를 두고, hotbar/focus 상태를 구독해 메시를 갱신한다.

### [질문 3]

1. `EngagedFocus` 에서 커서를 따라다니는 메시의 좌표 기준
- 질문 내용: `EngagedFocus` 상태에서 선택된 아이템 메시가 커서를 따라다닐 때, 이를 어떤 좌표 기준으로 움직일지 확정이 필요하다.
- 필요한 이유: 화면 기준 오프셋으로만 따라다니는지, 실제 월드 공간 특정 깊이 평면으로 투영하는지에 따라 구현 난이도와 상호작용 감각이 크게 달라진다.
- 선택지
  - 옵션 A: 카메라 기준 로컬 오프셋 메시로 처리하고, 화면 좌표를 카메라 앞 평면 오프셋으로 변환해 따라다니게 한다.
  - 옵션 B: 커서 위치를 월드로 디프로젝션해 실제 월드 공간의 고정 깊이 또는 충돌 지점으로 메시를 이동시킨다.
  - 옵션 C: 실제 3D 메시 대신 UI 표현에 가까운 단순 추종으로 처리하고, 월드 상호작용이 필요할 때만 별도 배치 프리뷰를 만든다.

- 필요한 이유: 현재 `UBeekeeperHotbarComponent` 는 선택/필터링/UI 상태 오너 역할에 가깝고, 여기에 소유 데이터까지 넣으면 책임이 섞인다. 반대로 별도 인벤토리를 두면 구조는 깔끔하지만 시스템이 하나 더 필요하다.

1. 획득 대상 월드 오브젝트 구조
